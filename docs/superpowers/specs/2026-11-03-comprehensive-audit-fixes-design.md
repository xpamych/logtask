# Дизайн последовательного исправления результатов аудита

Дата: 2026-11-03
Ветка: `fix/comprehensive-audit`

## Назначение

Устранить все подтверждённые проблемы из комплексного аудита Logtask, начиная
с рисков потери Markdown-данных и заканчивая UI, зависимостями, CI и
документацией. Работа ведётся по одной проблеме за раз: регрессионный тест,
исправление, профильные проверки, отдельный коммит.

## Цели

- Исключить destructive merge по неполным данным внешних API.
- Не сообщать об успешной синхронизации при ошибках записи и не портить state.
- Не допускать записи результатов синхронизации в другой граф.
- Усилить rename/delete страниц и сохранить Logseq round-trip.
- Восстановить мгновенный write-back статуса и корректность UUID IPC.
- Не перезаписывать повреждённые настройки и состояние интеграций молча.
- Исключить пропуск внешних изменений watcher'ом.
- Исправить перечисленные ошибки редактора, подборок и live-обновлений.
- Ограничить сетевые ответы и усилить атомарную запись.
- Обновить уязвимые JS-зависимости, сделать проверки CI обязательными и
  синхронизировать документацию с поведением.

## Не входит

- Переписывание архитектуры, переход на другую модель хранения или UI-framework.
- Новые возможности вне списка аудита.
- Изменение Markdown-формата и служебных свойств Logtask.
- Двусторонняя синхронизация полей, кроме уже заявленного статуса.
- Пагинация generic REST API без стандартного контракта: она неизвестна.
- Обязательная проверка настоящих внешних сервисов: сетевые сценарии покрываются
  wiremock; реальный граф пользователя не изменяется.

## Подходы

### Выбран: независимые последовательные коммиты

Каждый пункт получает собственный failing test, минимальное исправление,
проверку и коммит. Это увеличивает число коммитов, но позволяет независимо
откатывать рискованные изменения и ясно связывает их с результатами аудита.

### Альтернатива: крупные коммиты по подсистемам

Синхронизация, файловые операции, frontend и инфраструктура оформлялись бы
четырьмя пакетами. Так быстрее, но смешанные изменения труднее проверять и
откатывать. Пользователь выбрал первый подход.

## Общие ограничения

- Сохранять байт-точный round-trip нетронутых Markdown-фрагментов.
- Не расширять Tauri capabilities.
- Не добавлять зависимости, если задачу можно решить существующим стеком.
- Комментарии, UI, документация и сообщения коммитов — на русском.
- После каждого Rust-изменения: `cargo fmt`, профильные тесты, затем полный
  `cargo test --workspace` и `cargo clippy --workspace --all-targets -- -D warnings`.
- После каждого frontend-изменения: профильные Node-тесты, `npm run typecheck`,
  затем полный frontend test suite и `npm run build`.

## Этапы и отдельные коммиты

### 1. Полная пагинация форжей

Для Gitea, GitHub и GitLab добавить последовательную загрузку страниц репозиториев
и issues с `page=N`: до короткой/пустой сырой страницы, до фильтрации GitHub PR.
Сохранить существующие лимиты как размер страницы, стабильно дедуплицировать
репозитории. Ошибка любой страницы завершает fetch без merge. Fallback org → user
разрешён только по подтверждённому HTTP 404 на первом org-запросе; ошибка второй
и последующих страниц org не может переключиться на другой набор репозиториев.
Тесты wiremock: несколько страниц issues и репозиториев, точная кратная страница,
ошибка второй страницы, запрет destructive fallback.

### 2. Честная обработка ошибок записи и state в sync

Добавление задачи выполняется одной записью страницы: блок получает статус,
заголовок, приоритет и все `source*` свойства до единственной сериализации. При
ошибке не остаётся блока без идентификатора, который породил бы дубль на повторе.
`add_task`, `update_task`, удаление дублей/исчезнувших и `MarkMissing` возвращают
`Result`; счётчики меняются только после успеха. Ошибки `ensure_page` тоже не
позволяют продвинуть `last_sync`.

При ошибке заполнять `SyncReport.error`, сохранять прежний `TaskState` неудачной
задачи. `refresh_task_states` обновляет только успешные/no-op задачи. При любой
merge-ошибке `last_sync` не продвигается.

Все read-modify-write `integrations-state.json` сериализуются общей блокировкой.
После сетевых операций state перечитывается под блокировкой, изменяется только
текущий источник и сохраняется целиком, чтобы параллельные источники не затирали
друг друга. Ошибка `state::save` попадает в отчёт. Тесты: сбой второй части старого
сценария добавления, mtime-конфликт, ошибка MarkMissing/ensure_page/save state,
конкурентные источники и повтор без дублей.

### 3. Защита от смены графа во время синхронизации

В `AppState` добавить монотонный `graph_epoch`. `graph_load` и `graph_close`
увеличивают его до изменения root/graph; sync захватывает `{epoch, root}` в начале.
Перед merge проверять epoch под write-блокировкой графа. Если `graph_load` увеличил
epoch и ждёт блокировку, текущий sync может завершить запись только в согласованный
старый граф/root; после освобождения блокировки новые этапы уже не выполняются.
Проверки повторяются после await перед refresh/save state и перед reindex/event.
Ручной sync защищён тем же протоколом, не только `abort()` фоновой задачи.
Тесты: смена root после fetch, смена во время ожидания write-lock, закрытие графа.

### 4. Безопасные rename/delete страниц

Перед rename прочитать все затронутые файлы, захватить mtime и вычислить изменения.
Каждая запись непосредственно перед заменой повторно проверяет захваченный mtime;
ошибка metadata не fail-open. Создаются резервные данные для отката. При сбое
откатываются только файлы, у которых текущее состояние всё ещё совпадает с записью
Logtask; более новая внешняя правка не перезаписывается.

Если rollback невозможен или сам завершился ошибкой, команда возвращает список
несогласованных файлов и всегда запускает полную переиндексацию фактического
состояния. Таким образом, многофайловая транзакция остаётся best-effort, а не
ложной гарантией атомарности. `page_delete` получает mtime-проверку. Замена ссылок
пропускает inline/fenced code. Тесты: сбой на каждом файле, сбой rollback, внешняя
правка между preflight и записью, кодовые фрагменты.

### 5. Корректный write-back и UUID IPC

`task_set_status` извлекает `source`/`source-id` до `reload_page`, а fresh UUID
получает после переиндексации. `block_create` возвращает UUID из финального
графа, а не до него. Тесты: импортированная задача инициирует push, созданный
UUID существует в актуальном графе.

### 6. Явные ошибки повреждённых JSON

Отсутствующий `settings.json`/`integrations-state.json` по-прежнему означает
значения по умолчанию; невалидный JSON возвращает понятную ошибку и не
перезаписывается автоматически. Синхронизация при повреждённом state не запускает
merge. Обновить call sites и UI-обработку ошибок. Тесты: повреждённые файлы
сохраняют байты и возвращают ошибку, отсутствующие файлы работают как раньше.

### 7. Watcher без глобального окна подавления

Коалесцировать конкретные пути `.md`-событий; временные/non-md файлы atomic write
игнорируются, оба пути rename-события учитываются. В `Page` хранить хэш содержимого.
Собственное эхо пропускать только если путь и хэш содержимого соответствуют
актуальному индексу. Изменение содержимого с сохранённым mtime тоже вызывает
переиндексацию; отсутствующий/неизвестный файл обрабатывается по состоянию индекса.
Убрать правило «1,5 секунды после любой записи». Тесты: внешняя правка сразу после
собственной записи, тот же mtime с другим содержимым, rename и отсутствие лишней
переиндексации собственного эха.

### 8. Автодополнение и создание задачи

Вынести вставку автодополнения в чистую функцию: сохранять суффикс и ставить caret
после `]]`. Команда `mod+shift+t` открывает composer с маркером `TODO`; обычное
создание записи остаётся без статуса. Тесты на текст до/после ссылки и выбор
маркера команды.

### 9. Последовательное сохранение настроек и загрузка PageView

Все записи настроек, включая избранное и ширины, проходят через модель «один
in-flight + последний pending snapshot» с монотонным sequence. IPC выполняются
последовательно, устаревший ответ не меняет индикатор новой операции. Каждый снимок
привязан к root/epoch графа; `settings_save` проверяет root в Rust. При A → B
pending A отменяется, in-flight A не может записаться в B, сохранение B идёт после
завершения старого IPC. `PageView.load` получает epoch: устаревшие данные, backlinks
и ошибки отбрасываются. Тесты: порядок записи, дебаунс/запрос A при открытии B,
гонка страниц A → B.

### 10. Подборки, backlinks и inline code

При сохранении подборки передавать исходное название и заменять именно его.
`BacklinksPanel` получает `refreshKey`. Inline code распознаётся до ссылок/тегов/URL
и остаётся литеральным. Тесты на rename подборки, обновление backlinks, разную
длину backticks и fenced-блоки в trailing-строках.

### 11. CLOCK в карточках задач

Добавить `clockRunning` в Rust/TS `TaskDto`, передать `onClockToggle` из `TaskCard`
и обновлять fresh UUID/состояние после `clock_start`/`clock_stop`. Тесты DTO и
прикладного переключения.

### 12. Ограничение HTTP и надёжность atomic write

Добавить общий потоковый reader с пределами для title/favicon, JSON API и тел
ошибок. Проверять Content-Length, но не полагаться на него: chunked/ложный размер
тоже ограничивается фактическим числом прочитанных байт. Проверять HTTP(S) у
исходного и эффективного URL после redirects. Пределы задаются по типу ответа;
title не читается целиком ради первых 256 КиБ.

В atomic write ошибки восстановления permissions прекращают запись; на Unix ошибка
fsync родительской директории возвращается вызывающему. Тесты: отсутствующий и
ложный Content-Length, redirect на недопустимую схему, граница порций, большой
JSON/error-body и безопасный filesystem fault injection.

### 13. Зависимости, clippy и CI

Обновить lockfile в рамках существующих semver-ограничений до версий без
известных advisories; повторить `npm audit --omit=dev` и все проверки. Исправить
`field_reassign_with_default` в тесте настроек. Добавить CI для push/PR/tag:
`npm ci`, frontend tests/build, `cargo fmt --check`, clippy и Rust tests. Release
не должен обходить эти проверки.

### 14. Документация

Обновить `AGENTS.md`, README и `docs/01…05`: реальные capabilities, пагинация и
ошибки sync, поведение rename/delete, новая задача, CLOCK в карточках, watcher,
ограничения HTTP и актуальный статус backlog. Удалить несоответствие про
фиксацию WebKitGTK в `tauri.conf.json`. Документация изменяется в коммитах
соответствующих этапов; этот финальный коммит закрывает оставшиеся расхождения.

## Проверка результата

Финальные команды из корня worktree:

```bash
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
node --conditions=browser --test src/lib/graph/*.test.ts src/components/graph/*.test.ts src/lib/*.test.ts
npm run build
npm audit --omit=dev
```

Дополнительно проверить `git diff --check`, отсутствие временных файлов и чистый
`git status` после коммитов. GUI end-to-end выполняется только если доступное
окружение позволяет безопасно открыть отдельный тестовый граф; реальный граф
пользователя для проверки не используется.
